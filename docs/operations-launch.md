# Выпуск, копии и инциденты Dahar

Это процедура и локальные инструменты. Внешний backup, staging и оповещения ещё не считаются настроенными.

## Перед выпуском

1. Зафиксировать версию приложения и схему. Выполнить `npm run check`, `npm test`, `npm run test:e2e` в CI. Локально при ограничении watcher: `CHOKIDAR_USEPOLLING=1 npm run lint:fsd`.
2. Создать независимую копию PostgreSQL. `DATABASE_URL` передать через секрет окружения, `BACKUP_DIR` — каталог вне репозитория. Запустить `scripts/backup-db.sh`. Файл содержит личные данные и секреты сервиса: права 0600, зашифрованное внешнее хранилище, доступ только операторам.
3. При S3 отдельно обеспечить versioning/резервирование объектов. SQL-копия содержит ссылки на S3, не сами объекты. Пользовательский JSON-export включает прикреплённые изображения.
4. Восстановить копию в пустую БД с окончанием `_restore_test`: `RESTORE_DATABASE_URL` + `scripts/restore-drill.sh /path/copy.dump`. Проверить число записей, вход тестового аккаунта, изображения, связи и экспорт. Измерить время. Не использовать `--clean` в production.
5. Проверить staging на той же версии PostgreSQL и Node. `SMOKE_URL=https://staging.example npm run smoke`. Дополнительный smoke-аккаунт не должен содержать личных данных; логин/пароль только в секретах окружения.
6. Выпускать web и worker одной версии. Не запускать старый код, который пишет данные, после изменения формата очереди. Миграция 008 добавляет поля и таблицы; существующие финансы остаются видимыми.
7. Проверить readiness `/api/ready`, web `/`, `/welcome`, `/admin`, фоновые напоминания, очередь, экспорт, dashboard админки. После выпуска смотреть ошибки и p95.

## Откат

Сохранить предыдущий образ/commit до выпуска. Для отката приложения остановить worker новой версии, вернуть web/worker проверенной предыдущей версии и выполнить smoke. Добавленные таблицы не удалять ради отката. Перед откатом оценить совместимость с новыми полями, подписью импорта и версиями набора данных: старые web/worker не знают этих защит. Если прежняя версия их не поддерживает — выключить запись и выпускать исправление вперёд, вместо отката в уязвимую версию.

После повреждения данных остановить запись и фоновые задачи; сохранить копию повреждённой БД для диагностики; восстановить в отдельную базу; проверить; переключить приложение. Не восстанавливать поверх работающей базы. Повторно проверить ключи Telegram/VAPID/AI и S3. Сообщение пользователям готовит владелец по фактическим последствиям.

## Секреты и подключения

- Production использует HTTPS и Secure cookie. Секреты передаются через окружение/secret store, не коммитятся и не печатаются.
- `PGSSL=true` включает проверку сертификата. Для частного CA использовать доверенный CA окружения Node, а не отключать `rejectUnauthorized`.
- `REGISTRATION_ENABLED=true` действует только с `TERMS_URL` и `PRIVACY_URL`. Сначала опубликовать проверенные документы и настроить поддержку. Не выдавать пробный период за полноценный биллинг.
- `AI_MONTHLY_LIMIT` по умолчанию 4 успешных разбора в календарный месяц UTC. При неуспехе месячная квота возвращается; дневной аварийный лимит 10 попыток сохраняется. `AI_DAILY_SERVICE_LIMIT` по умолчанию 100 попыток на сервис. Остаток месячной квоты виден в обзоре.
- Журнал AI доступен администратору через `/api/admin/ai-usage`: токены, ошибки, задержки и непроценённые запросы. Для расчёта стоимости задать `AI_PRICE_MODEL` с точным именем возвращаемой модели и `AI_INPUT_USD_PER_MILLION`, `AI_OUTPUT_USD_PER_MILLION`, `AI_CACHE_WRITE_USD_PER_MILLION`, `AI_CACHE_READ_USD_PER_MILLION`. Ставки сверяет владелец с действующим договором; без них стоимость остаётся неизвестной. Повтор успешного Idempotency-Key возвращает сохранённый ответ, генерации одного аккаунта сериализуются через lease в БД.
- Web Push разрешает известные домены FCM, Mozilla, Apple, Windows. Для другого провайдера добавить точный доверенный домен и тесты. Произвольные URL запрещены.

## Хранение

Идемпотентные ответы и подтверждения уведомлений: 30 дней. Допустимая автоматическая отправка офлайн-очереди: 28 дней; более старые изменения остаются на устройстве для ручной проверки. История отмены и журнал AI: 90 дней. Продуктовые дневные счётчики: 400 дней. Лог ошибок: 30 дней. Очистка запускается worker раз в час. Автокопии перед восстановлением: последние 10 на аккаунт; они в основной БД и не заменяют внешний backup.

Удаление аккаунта удаляет связанные SQL-записи по FK, сессии, настройки и данные. S3-объекты очищает существующая процедура удаления orphan files; независимые копии требуют отдельного срока хранения и защиты от повторного появления удалённых аккаунтов при disaster restore. Зафиксировать этот срок в политике до публичного запуска.

## Оповещения и дежурство

Настроить внешний HTTPS-check `/api/ready` раз в минуту; уведомление после трёх сбоев. Подключить существующий Sentry для web/server, без содержимого задач и выписок. Настроить сигнал на 5xx, недоступность БД, остановку worker, неудачную копию и рост AI-расхода. Назначить получателя и запасной канал. Это действия в инфраструктуре, а не выполненная настройка.

При инциденте записать время, версию и симптом; проверить readiness/DB/worker/сеть; выключить проблемную дорогую функцию; исправить или переключить проверенную версию; выполнить smoke; проверить очередь и данные. После восстановления описать причину и одну проверяемую меру предотвращения.

Цели RPO 15 минут и RTO 2 часа остаются гипотезами до подключения PITR и фактического учения на production-объёме.
