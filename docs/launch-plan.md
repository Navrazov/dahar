# План подготовки Dahar к запуску

Дата: 6 октября 2026. Основание: `docs/audit-2026-10-06.md`.

Документ задаёт целевую версию и порядок работ. Пункты не являются выполненными исправлениями. Сроки — предварительные оценки, без обязательства выпустить продукт к определённой дате.

## 1. Решение о продукте

### Аудитория и обещание

Начальная аудитория: русскоязычные самостоятельные специалисты с несколькими личными и рабочими проектами, которые регулярно используют Telegram.

Обещание: **«Выбери главное на день, быстро записывай дела и каждую неделю понимай, что получилось».**

Главный цикл: записать → выбрать главное → выполнить → разобрать неделю → составить следующий план.

Начальный тариф: 299 ₽/месяц или 2 990 ₽/год. Пробный период 14 дней без карты. Один тариф, четыре AI-разбора в месяц после подтверждения себестоимости. Это гипотеза цены; пересматривать по покупкам, продлениям и расходам.

### Состав запуска

| Возможность                                                 | Решение                                                                                                   |
| ----------------------------------------------------------- | --------------------------------------------------------------------------------------------------------- |
| Сегодня, задачи, проекты                                    | Основной продукт                                                                                          |
| Привычки, итоги недели                                      | Основной продукт                                                                                          |
| Telegram, PWA, Mini App                                     | Основные способы использования                                                                            |
| Цели                                                        | Простые цели внутри проектов; не усложнять первый запуск                                                  |
| Финансы                                                     | Дополнительный модуль, выключенный до выбора пользователя; проверка валюты обязательна                    |
| Партнёры, трейдинг, бизнес, контент                         | Сохранить для существующих пользователей, убрать из первого знакомства и лендинга; не развивать до спроса |
| Калькулятор                                                 | Инструмент внутри финансов                                                                                |
| Google Calendar                                             | Желательное улучшение после пилота; отсутствие не блокирует запуск, если обещание честное                 |
| Командная работа, нативные приложения, универсальный AI-чат | После подтверждения спроса                                                                                |

Никакие пользовательские данные не удаляются при упрощении интерфейса. Отключение модуля сохраняет данные, а повторное включение возвращает доступ к ним.

### Приоритеты

- **P0:** закрыть до доступа платных пользователей — приватность, потеря данных, финансовая точность.
- **P1:** закрыть до публичного самостоятельного запуска — ежедневный сценарий, аккаунты, платежи, эксплуатация, поддержка.
- **P2:** улучшать после пилота — интеграции, расширенное планирование и оптимизация по реальным объёмам.
- **P3:** не включать в текущий план реализации без доказанного спроса.

## 2. Этап A — сохранность и доверие, P0

Оценка: 5–8 рабочих дней. Результат: существующие сценарии безопасны для закрытого платного пилота.

| ID  | Работа                                                                                               | Критерий приёмки                                                                                                                                                          |
| --- | ---------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| A01 | Изолировать React Query и IndexedDB по владельцу, обработать смену аккаунта и события другой вкладки | A → B, выход, перезагрузка и офлайн не показывают данные A под именем B; очередь не отправляется другому владельцу                                                        |
| A02 | Определить режим запуска офлайн и подтверждения личности                                             | Показываются данные только ранее подтверждённого владельца этого локального хранилища; вход другим пользователем требует сети; восстановленная сессия согласуется с кэшем |
| A03 | Сохранять валюту выписки в результате парсинга и проверять перед commit                              | Выписка USD отклоняется в рублёвом аккаунте; суммы в валюте счёта проверяются; Telegram использует те же правила                                                          |
| A04 | Защитить черновики итогов недели                                                                     | Refetch и изменения другой вкладки не заменяют dirty-форму; смена недели и уход со страницы обрабатывают несохранённые изменения                                          |
| A05 | Исправить service worker                                                                             | `/admin`, `/tg` и ошибочный HTML не заменяют оболочку клиента; переход в админку и последующий запуск офлайн проходят                                                     |
| A06 | Обновлять финансовые сводки при изменении бюджетов                                                   | Создание, редактирование и удаление сразу меняют список, лимиты и счётчики превышений                                                                                     |
| A07 | Различать ошибку загрузки и пустой список                                                            | При 503 пользователь видит сбой и повтор; ранее полученные данные сохраняются с понятным статусом                                                                         |
| A08 | Нормализовать доменные конфликты бюджета                                                             | Повтор категории даёт понятное сообщение и 409, а не 500; регистр/пробелы согласованы с расчётом расходов                                                                 |
| A09 | Передавать AI полные счётчики независимо от выборки названий                                         | 49 выполненных задач представлены как 49; усечение списков отмечено; предыдущий и текущий периоды сопоставимы                                                             |

Добавить регрессионные тесты именно на воспроизведённые ошибки. Текущие серверные, клиентские и браузерные проверки должны остаться зелёными.

Перед сменой структуры локального хранилища сохранить совместимость с существующей офлайн-очередью. Не стирать ещё не отправленные изменения при миграции кэша.

## 3. Этап B — эксплуатационная надёжность, P1

Оценка: 6–10 рабочих дней. Частично можно выполнять рядом с этапом C; открытый приём платежей зависит от завершения критичных пунктов.

| ID  | Работа                                                                        | Критерий приёмки                                                                                                                                                    |
| --- | ----------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| B01 | Убрать внешнюю отправку уведомлений из длительной пользовательской транзакции | Недоступный Telegram не блокирует редактирование задач; claim и фиксация результата используют короткие транзакции                                                  |
| B02 | Подтверждать Web Push по устройству                                           | Успех телефона не закрывает повтор для компьютера; отключённые endpoint удаляются; повтор не дублирует уже подтверждённые доставки                                  |
| B03 | Общие лимиты входа, генераций и регистрации                                   | Лимиты действуют суммарно на двух web-экземплярах и не исчезают после рестарта                                                                                      |
| B04 | Определить модель времени аккаунта                                            | Web, Telegram, Mini App, привычки и обзоры одинаково определяют день; проверены Москва, пояс с отрицательным смещением и переход летнего времени                    |
| B05 | Определить срок хранения истории и операций                                   | История, подтверждения и технические ответы имеют измеримый срок и процедуру очистки; срок идемпотентности покрывает допустимый возраст очереди и повторные попытки |
| B06 | Защитить изменения после восстановления копии                                 | Старая очередь не меняет новые записи с совпавшими ID; есть версия набора данных или эквивалентная защита                                                           |
| B07 | Ограничить ресурсы аккаунта                                                   | Размер файлов, число подписок, импорт и частота дорогих действий ограничены на сервере и объяснены в UI                                                             |
| B08 | Проверить внешние URL и загрузки                                              | Push endpoint и другие обращения не позволяют обращаться к внутренним адресам; ключи и входные данные полноценно валидируются                                       |
| B09 | Проверить секреты, TLS и логи                                                 | Секреты не попадают в логи/экспорт; сертификаты соединений проверяются; разделены окружения разработки и production                                                 |
| B10 | Независимые резервные копии                                                   | Включён внешний backup; выполнено восстановление в отдельную базу, включая файлы; задокументированы фактические RPO/RTO                                             |
| B11 | Метрики и уведомления владельцу                                               | Видны 5xx, задержки, недоступность БД, очередь, сбои уведомлений, ошибки frontend и AI-расходы; маршруты оповещения настроены                                       |
| B12 | Процедура выпуска и отката                                                    | Есть staging, smoke-проверка, безопасная миграция, откат версии приложения и порядок восстановления при несовместимой миграции                                      |

Предварительные цели для первых сотен пользователей: доступность 99,5% за месяц, восстановление сервиса до двух часов, допустимая потеря данных при аварии до 15 минут при доступном PITR. Это целевые показатели: подтвердить возможностями инфраструктуры и практической проверкой, а не обещать заранее.

Не вводить большой новый инфраструктурный стек без необходимости. Для текущего масштаба использовать PostgreSQL и существующий монолит, добавляя отдельные компоненты только при измеримой потребности.

## 4. Этап C — ежедневный сценарий и интерфейс, P1

Оценка: 8–12 рабочих дней. Результат: человек начинает пользоваться без объяснения владельца.

### Первый запуск

- C01: новая установка показывает только ядро; дополнительные направления включаются осознанно.
- C02: первая полезная задача создаётся за 90 секунд или быстрее в наблюдении минимум за пятью новыми людьми.
- C03: привычка, Telegram и PWA предлагаются после первой задачи; все предложения можно пропустить.
- C04: демо-данные отделены от настоящих записей; их удаление не затрагивает созданное пользователем.
- C05: дать три стартовых шаблона — рабочая неделя, личный проект, привычка; не превращать начало в настройку всей жизни.

### Задачи и проекты

- C06: быстрый ввод, перенос срока, завершение и отмена работают на компьютере и телефоне.
- C07: явно различать «когда планирую делать» и крайний срок; если пока одно поле — честно обозначить его смысл.
- C08: добавить простую длительность задачи и чек-лист; правила повторения описаны и проверены на конце месяца и високосном годе.
- C09: три главные задачи можно выбрать, заменить и снять; дневной план сохраняется после перезапуска и синхронизации.
- C10: просроченные дела можно перенести, закрыть или убрать; исключить давление бесконечным красным списком.
- C11: активные проекты отличаются от архива; завершение и удаление не дают неожиданных каскадных потерь.

### Привычки и неделя

- C12: пропуск, подтверждение и срыв имеют одинаковый смысл в web, Telegram и Mini App.
- C13: прошлые периоды корректно учитывают начало привычки; изменение расписания и архивирование имеют явную семантику для истории.
- C14: обзор за 5–10 минут показывает полные числа, завершённые дела и небольшой следующий план.
- C15: заметки сохраняются как черновик локально и/или на сервере; удаление черновика осознанное.
- C16: предложения AI превращаются в задачу через редактируемую форму; повторное нажатие не создаёт неожиданные дубли.

### Мобильная версия и доступность

- C17: физически проверить Safari/PWA на iPhone, Chrome/PWA на Android и Telegram на обеих платформах.
- C18: клавиатура не закрывает сохранение, нижняя панель не перекрывает контент, формы не вызывают горизонтальную прокрутку.
- C19: проверить основные сценарии с клавиатуры и экранным диктором; подписи полей, фокус, ошибки и контраст доступны.
- C20: использовать единые состояния loading/error/empty/stale и понятные сообщения во всех основных разделах.

Приёмка: как минимум четыре из пяти новых участников без подсказок создают дело, выбирают главное, завершают задачу и находят итоги недели. Это маленький качественный тест, не статистическое подтверждение конверсии.

## 5. Этап D — аккаунты и подписка, P1

Оценка: 8–12 рабочих дней плюс ожидание подключения платёжного провайдера и подготовки документов.

### Доступ

- D01: начать с самостоятельного входа по приглашению; снять ограничение после проверки защиты от злоупотреблений.
- D02: добавить проверенный канал восстановления аккаунта, подтверждение адреса/владения и одноразовые ограниченные по времени токены.
- D03: пользователь видит свои сессии и может завершить остальные; смена пароля и блокировка ведут себя согласованно.
- D04: подтвердить политику 2FA для Telegram-входа и чувствительных действий; привязка Telegram требует доказательства владения аккаунтом.
- D05: самостоятельный экспорт и удаление аккаунта с понятными последствиями; удаление охватывает связанные данные и файлы по задокументированной политике.

### Платежи

- D06: выбрать один провайдер после определения страны продавца, рынка покупателей и доступных способов оплаты; не строить несколько интеграций.
- D07: тарифы и права доступа проверяются на сервере, даты trial/paid_until хранятся в БД.
- D08: реализовать состояния trial, active, cancel_at_period_end, past_due и expired с понятным UI.
- D09: webhook проходит проверку подлинности и обрабатывается идемпотентно; повтор, задержка и события не по порядку не дают двойную оплату или потерю доступа.
- D10: возврат из платёжной формы не считается доказательством оплаты; доступ включается по подтверждённому событию провайдера.
- D11: автоматическое продление требует явного согласия; отмена доступна самостоятельно и сохраняет оплаченный остаток периода.
- D12: возвраты, сбой списания и сверка платежей имеют проверенный процесс; владелец видит расхождения.
- D13: после окончания оплаты доступны чтение и экспорт; записи не удаляются автоматически из-за неоплаты; платные изменения и AI ограничены сервером.
- D14: сохранять дату, цену и версию согласованных условий подписки; изменения цены не скрыты от действующего клиента.

### Документы и помощь

- D15: подготовить условия, политику данных, возвраты, сведения о продавце и требования к платежам с учётом выбранной юрисдикции; перед запуском проверить их у соответствующего специалиста.
- D16: явно описать, какие данные уходят в AI; отказ от AI не мешает пользоваться основными функциями.
- D17: разместить контакт поддержки, статус сервиса и инструкции по аккаунту, PWA, Telegram, отмене и экспорту.

Пилот допускает ручной платёж и выдачу доступа, если пользователю заранее понятны срок, стоимость, продление и помощь. Публичный самостоятельный запуск требует D06–D14.

Приёмка: тестовые первая оплата, повтор webhook, неуспешное списание, продление, отмена, возврат и окончание trial от начала до конца дают правильные права доступа; данные доступны для экспорта во всех состояниях.

## 6. Этап E — AI, финансы и большие объёмы

Оценка: 5–8 рабочих дней на необходимые для запуска пункты; расширения P2 оценить отдельно.

### AI — P1

- E01: общая квота в БД, ограничение одновременно выполняемых генераций и идемпотентность платного запроса.
- E02: учитывать input/output tokens, стоимость и задержку; установить максимальные расходы на аккаунт и на сервис.
- E03: при неуспехе показывать повтор; определить правила возвращения пользовательской квоты, сохраняя фактическую стоимость вызова.
- E04: сохранить полезную ручную сводку при недоступности модели; AI не блокирует обзор недели.
- E05: сравнить модели на одном наборе примеров и выбрать достаточное качество по измеренной цене; название модели само по себе не критерий.
- E06: проверять структуру ответа и корректность чисел; тексты пользователя трактуются как данные, а не инструкции для модели.
- E07: подготовить минимум 30 контрольных недель: пустая, активная, больше 40 задач, начало привычки, архив, отключённый модуль, расходы без дохода, смена месяца.

Приёмка: ключевые числа всегда соответствуют агрегатам; система не создаёт новые дела без действия пользователя; расход и остаток квоты видны владельцу.

### Финансы — P1 для доступного модуля

- E08: импорт показывает распознанный банк, валюту, период, пропущенные строки, дубли и предполагаемые переводы.
- E09: неоднозначные переводы не объединяются без понятного подтверждения; пользователь может отменить импорт.
- E10: проверить округление, отрицательные суммы, дубли одинаковых покупок и перекрывающиеся выписки.
- E11: не обещать мультивалютность, банковскую автосинхронизацию или бухгалтерский учёт, которых нет.

### Объёмы — P1 и P2

- E12 (P1): отключённые модули не скачиваются на обзоре недели; недельные показатели считаются по периоду.
- E13 (P1): проверить аккаунт с 10 000 задач, 50 000 отметок привычек и 20 000 финансовых операций на отдельной тестовой базе.
- E14 (P1): основной экран не требует полной загрузки истории; p95 обычных чтений до 500 мс на оговорённом стенде при 50 одновременных активных сессиях — предварительная цель.
- E15 (P2): виртуализация больших списков, дополнительные индексы и более дорогие агрегаты только после профилирования.

В отчёте нагрузки фиксировать железо, размеры данных, число сессий, сценарии и реальные результаты. Тестировать отдельно нормальную нагрузку и деградацию внешних сервисов.

## 7. Этап F — аналитика и проверка спроса, P1

Оценка: 3–5 рабочих дней подготовки, затем 4–8 недель наблюдения. Подготовку делать до пилота.

### Определения метрик

- **Активированный:** создал собственную задачу и выполнил её в первые 48 часов после первого входа.
- **Полезно активный за неделю:** в разные дни совершил хотя бы два действия — выбрал/выполнил задачу, подтвердил привычку или сохранил обзор. Одно открытие страницы не считается.
- **MAU по полезным действиям:** уникальные пользователи с хотя бы одним таким действием за последние 30 дней.
- **W4 retention:** доля активированных из конкретной когорты с полезным действием на четвёртой неделе. Показатель отделён от retention по простому посещению.
- **Первая повторная оплата:** успешное продление среди помесячных клиентов, у которых уже наступила дата продления; годовые клиенты не входят в знаменатель.

Включить события signup/invite, first_task_created, task_completed, focus_selected, habit_logged, telegram_linked, review_saved, trial_started, checkout_started, payment_succeeded, renewal_succeeded, cancellation и export. Повтор доставки события и офлайн-синхронизация не удваивают статистику. В аналитику не отправлять названия задач, содержимое заметок и банковские описания.

### Пилот

1. Пригласить 20–30 людей одного сегмента, часть вне личного круга владельца.
2. Наблюдать пять первых запусков; исправить повторяющиеся затруднения.
3. Получить реальные оплаты; не обещать функцию ради единственного покупателя.
4. Каждую неделю выяснять, что люди делают без напоминания владельца и почему пропускают обзор.
5. После trial отдельно исследовать купивших, отказавшихся и переставших пользоваться.
6. Наблюдать хотя бы первую повторную оплату помесячной подписки.

Первоначальные внутренние ориентиры: активация 60%, W4 retention активированных 40%, два сохранённых обзора за первый месяц у 25% активированных. Это гипотезы, не нормы рынка. Всегда показывать абсолютные числа, размер выборки и зрелость когорты.

### Разрешение масштабировать привлечение

Переходить к заметным рекламным расходам после нескольких последовательных когорт, измеренной стоимости обслуживания и появления повторных оплат. Рабочие ориентиры для обсуждения: не менее 100 активированных, не менее 30 помесячных клиентов с наступившей датой продления, первая повторная оплата от 75%, переменные расходы до 25% признанной выручки, окупаемость привлечения до трёх месяцев маржинального дохода. Маленькие выборки дают широкий разброс; один процент не определяет решение.

Если удержание слабое, следующий спринт решает конкретную причину ухода. Дополнительные модули не считаются автоматическим лекарством.

## 8. Этап G — упаковка и публичный запуск, P1

Оценка: 4–6 рабочих дней; материалы готовить во время пилота, финальные обещания уточнять по его результатам.

- G01: лендинг с одной аудиторией, одним обещанием и реальным сценарием; один главный призыв начать пробный период.
- G02: показать реальные экраны и короткое видео «записал → выбрал → сделал → разобрал неделю».
- G03: объяснить название Dahar одной фразой; проверить, понятно ли произношение и запоминается ли имя.
- G04: публичная цена, условия trial, отмена, экспорт, поддержка и ограничения доступны до покупки.
- G05: публиковать отзывы только с разрешения, без придуманных чисел и логотипов.
- G06: выпустить короткие инструкции по старту, Telegram, PWA, офлайн, обзору и финансам.
- G07: первые каналы — личный контент, тематические сообщества и небольшие партнёрства; тестировать один сегмент и одно сообщение за раз.
- G08: фиксировать источник и стоимость привлечения до оплаты; бюджет каждого эксперимента и предел потерь определить заранее.
- G09: перед объявлением проверить все ссылки, оплату на телефоне, поддержку и процедуру инцидента.
- G10: после запуска семь дней ежедневно смотреть ошибки, отмены, очередь, оплату и новые затруднения.

Цель первой публичной волны — первые 100 платящих пользователей с понятными причинами покупки и регулярного использования. Это целевой этап бизнеса, не обещание результата.

## 9. Финальная проверка выпуска

### Автоматические проверки

- Форматирование, ESLint, TypeScript, FSD, сборки, серверные/клиентские тесты и E2E проходят в CI.
- Регрессии этапа A включены в постоянный набор.
- Платежи проверяются на дублях, ошибках и событиях не по порядку.
- Нагрузочные сценарии и имитация отказов выполняются на отдельном стенде.

### Проверки человеком

- Компьютер: Chromium, Safari и Firefox — вход, создание, завершение, обзор, оплата, экспорт.
- Физические iPhone/Android: браузер, PWA и Telegram — клавиатура, навигация, уведомления, повторный вход.
- Нет сети: запуск с кэша, создание связанной записи, восстановление сети, две вкладки, ошибка валидации, смена владельца.
- Данные: отмена удаления, импорт/повтор выписки, восстановление копии, уход и возврат после окончания подписки.
- Авария: недоступность БД/AI/Telegram, рестарт worker, откат web-версии и фактическое восстановление backup.

## 10. Условия трёх запусков

### Закрытый платный пилот

- Все A01–A09 выполнены и проверены.
- Есть внешний backup и рабочая поддержка.
- Срок и стоимость доступа понятны; деньги учитываются, возможен возврат.
- Аналитика полезных действий включена.
- Известные ограничения явно сообщены участникам.

### Публичный самостоятельный запуск

- Все критичные P1 приняты; нет известных дефектов приватности, потери пользовательских изменений и неправильного платного доступа.
- Покупка, отмена, восстановление доступа и экспорт работают без владельца.
- Есть проверенная процедура восстановления, мониторинг, контакты и документы.
- Пользователи пилота самостоятельно проходят основной цикл; есть реальные оплаты.
- Календарь и дополнительные модули описаны ровно в пределах возможностей.

### Масштабирование

- Удержание, повторные оплаты и расходы измерены на зрелых когортах.
- Один канал привлечения даёт понятную стоимость платящего клиента.
- Поддержка и инфраструктура выдерживают рост.
- На каждом шаге расход ограничен заранее определённым бюджетом.

## 11. Сроки и ответственность

Предварительно: закрытый пилот через 4–6 недель, публичная версия через 10–14 недель, если работает один опытный разработчик полный день, а владелец ежедневно занимается пользователями, решениями, платежами и материалами. Интеграции, проверка провайдера и результаты пилота могут увеличить сроки.

| Период       | Основной результат                                                                 |
| ------------ | ---------------------------------------------------------------------------------- |
| Недели 1–2   | Решения о версии, исправления A, backup, наблюдаемость, аналитика                  |
| Недели 3–4   | Основной UX, мобильная проверка, приглашения и восстановление доступа              |
| Недели 5–6   | Закрытый платный пилот, платежи, квоты AI и эксплуатационные доработки             |
| Недели 7–10  | Удержание пилота, первая повторная оплата, исправления по причинам ухода, нагрузка |
| Недели 11–14 | Самостоятельная продажа, упаковка и ограниченный публичный запуск                  |

Разработчик отвечает за реализацию и доказательства приёмки. Владелец — за аудиторию, пользователей пилота, цены, продавца, бюджет и решения об обещаниях продукта. Для правовых/платёжных условий привлекается подходящий специалист. Общий статус хранить в этом документе или трекере: задача считается готовой только с результатом проверки.

Не ждать абстрактных 100/100: выпустить безопасный и законченный основной сценарий, затем улучшать его по поведению покупателей.
